# 2026-08-09 TX/RX 이더넷 직결 실제 화면 실기검증

## 최종 결론

TX/RX 영상 Ethernet을 공유기 경유에서 보드 간 직결로 바꾼 구성은 동작한다. 다만 1차 계측 때는 로그와 HDMI carrier만 보고 정상으로 잘못 판정했다. 실제 PC 캡처 창을 만든 뒤 확인하니 당시 화면은 정지해 있었다.

직접 원인은 케이블 link flap 뒤 양쪽 `udhcpc`가 유선 고정 주소를 삭제한 것이었다. 중복 주소가 없음을 확인하고 TX `10.10.15.2/24`, RX `10.10.15.3/24`만 다시 추가하자 서비스 재시작·보드 reset 없이 전송과 실제 화면이 즉시 재개됐다.

복구 뒤 최종 결과는 다음과 같다.

- TX PCam → AES-GCM → 직결 Ethernet → AES-GCM → RX HDMI → USB 캡처보드 → PC 실제 decoded pixel 경로 PASS
- 15초 동안 RX `450 frames`, 정확히 `30.0 fps`
- 300-frame 최소 조건 충족
- `auth/replay/status/queue/stale` 증가 0
- 안정 구간 `lost total 811 → 811`, 추가 loss 0
- TX PCam rolling color bar가 PC 원본 두 프레임에서 서로 다른 위치로 이동함을 확인
- 시험 뒤 PCam test pattern은 양쪽 active subdevice 모두 `0 (Disabled)`로 복귀

## 구성

```text
영상: TX 10.10.15.2/24 <-> RX 10.10.15.3/24 (직결, UDP 5602)
세션 제어: `<SESSION_CONTROL_SSID>` Wi-Fi
Secure Session: 양쪽 동일 872c2e44, counter 1
HDMI: RX 720p60 carrier -> USB3.0 capture -> PC
실제 source/content update: 약 30 fps
```

영상 route에는 gateway를 뜻하는 `via`가 없고, 상대 MAC은 TX `02:00:00:00:00:02`, RX `02:00:00:00:00:03`이다.

## 1차 판정 오류

1차 확인에서는 보드 로그의 frame counter, NIC packet/byte 증가, DirectShow 720p60 carrier, 저장 이미지 파일의 fingerprint만 확인했다. 이것만으로는 PC에 표시되는 decoded pixel이 움직인다는 것을 증명하지 못한다.

실제 decoded 원본을 5초 간격으로 다시 비교한 결과 두 파일이 byte-for-byte 동일했다.

```text
before_recovery_start.png
926B3C5ED41B622333FF0002084F0436A781EBA703DBCFCDBA160F49B90F91E3

before_recovery_after_5s.png
926B3C5ED41B622333FF0002084F0436A781EBA703DBCFCDBA160F49B90F91E3
```

따라서 이전 문구인 “carrier와 화면 내용이 계속 갱신되어 freeze가 없다”는 폐기한다.

## freeze 원인

정지 당시 RX 상태는 다음과 같았다.

- RX wired NIC는 L2 packet을 계속 수신
- RX `PIPE processed=203640`에서 정지
- RX log는 `UDP peer unavailable; retrying discovery` 반복
- RX `10.10.15.3/24` 주소가 인터페이스에서 사라짐
- IP `InAddrErrors`만 증가하고 UDP `InDatagrams`는 증가하지 않음
- VDMA는 error 없이 PARK0의 마지막 프레임을 반복 출력

TX `10.10.15.2/24`도 같은 방식으로 사라져 있었다. `/etc/network/interfaces`의 generic Ethernet DHCP가 `udhcpc -n -i enx000a35001e53`를 실행하고 있었고, link flap 뒤 애플리케이션 init이 넣은 고정 주소를 deconfig했다.

즉 VDMA/HDMI 정지는 원인이 아니라 완전한 UDP frame이 더 이상 RX 앱에 전달되지 않은 결과였다.

## 안전 복구와 네트워크 확인

양쪽에서 상대 주소에 ping 3회를 보내 reply 0, neighbour `INCOMPLETE`로 중복 사용자가 없음을 먼저 확인했다. 그 뒤 다음 주소만 다시 추가했다.

```text
TX: ip addr add 10.10.15.2/24 dev enx000a35001e53
RX: ip addr add 10.10.15.3/24 dev enx000a35001e53
```

서비스 restart, session 재생성, PL reset, 보드 reboot는 하지 않았다.

복구 뒤 TX→RX ping은 3/3 성공했고 평균 RTT는 0.829 ms였다. RX endpoint는 `10.10.15.3:5602 <-> 10.10.15.2:5602`를 유지했으며 socket drop은 0이었다.

## 450-frame 성능·오류 검증

15초 연속 관찰 결과:

| 항목 | 시작 | 종료 | 증가 |
|---|---:|---:|---:|
| RX processed | 207,960 | 208,410 | 450 |
| UDP InDatagrams | 6,508,025 | 6,522,394 | 14,369 |

`450 / 15 s = 30.0 fps`이므로 target `>=29.5 fps`와 hard gate `>=29.0 fps`를 모두 통과했다.

```text
auth_fail=0
replay_reject=0
status_fail=0
queue_overrun=0
stale=0
UDP RcvbufErrors=0
UDP InCsumErrors=0
UDP MemErrors=0
lost total=811 -> 811
```

VDMA PARK와 HDMI frame status도 다시 전진했다. `lost total=811`은 케이블 교체와 주소 유실 중 생긴 과거 누계이며 위 안정 구간에서는 증가하지 않았다.

## PC 실제 영상 검증

Desktop의 `jetson_to_pc\preview.py`로 `USB3. 0 capture`의 decoded BGR 프레임을 실제 Windows 창에 표시했다. 이 프로그램은 carrier FPS와 실제 pixel change를 별도로 표시하며 같은 화면만 반복되면 `PIXELS STATIC`으로 판정한다.

복구 뒤 일반 PCam 영상에서:

```text
1280x720 MJPG
HDMI carrier 약 58.5~60.0 fps
decoded pixel change 약 29.0~29.5 events/s
read failures=0
```

센서 노이즈를 움직임으로 오인하지 않도록 TX PCam의 `Color bars w/ rolling bar`를 약 7초간 켜고 자동 복귀 watchdog을 걸었다. PC 캡처 원본 두 장에서 rolling bar의 세로 위치가 명확히 달랐다.

```text
rolling_pattern_a.png
D4C0747B1A827110C23B4038D6E0EFFC87A60A181D9AA19627AA502411FEB1D7

rolling_pattern_b.png
76072FD69C826ED456D4DFA5112016901DCA736297ACAF87A2F5E79F49DCC7DB
```

`rolling_pattern_preview_a.png`와 `rolling_pattern_preview_b.png`에는 실제 프레임, carrier FPS, pixel delta, change-event rate가 함께 기록돼 있다. 이것으로 단순 register/log 값이 아니라 PC 표시 종단까지 실제 영상 내용이 움직임을 확인했다.

두 원본의 OpenCV decoded-pixel 비교 결과는 `exact_equal=False`, 평균 BGR 절대차 `9.378456`, 임계값 8 이상 변화 픽셀 `43,538 / 921,600 (4.7242%)`였다. JPEG 파일 byte나 metadata만 다른 것이 아니라 decoded 화면 픽셀 자체가 달랐다.

위 PNG들은 검증 중 직접 열어 확인한 뒤 SHA-256과 정량 결과만 이 문서에 남기고, 사용자 지시에 따라 Desktop 캡처 폴더에서 모두 삭제했다.

## 남은 운용 주의

- 현재 실행 중인 보드는 주소가 복구돼 정상이다.
- 프로젝트에는 TX `10.10.15.2`, RX `10.10.15.3` role-static `init-ifupdown` override와 generic wired DHCP 금지 release gate를 추가했고 `verify_release.ps1 -Quiet` 213개 검사를 통과했다.
- 현재 실행 중인 `image.ub`는 위 수정 전에 만들어진 파일이므로, 새 TX/RX PetaLinux image를 빌드·부팅하기 전에는 케이블 재연결 후 주소가 다시 사라질 수 있다.
- PetaLinux 2025.2 도구와 입력은 준비돼 있지만 WSL VHDX가 있는 C: 물리 여유가 약 7.3 GB뿐이어서 fresh 양쪽 Yocto build는 시작하지 않았다. 충분한 물리 공간을 확보하거나 WSL distro를 여유 있는 디스크로 옮긴 뒤 재빌드한다.
- 직결 운용 중에는 항상 TX `10.10.15.2/24`, RX `10.10.15.3/24` 존재를 먼저 확인한다.
- Jetson telemetry 기본 목적지 `10.10.15.1:47000`은 직결 케이블에서 도달하지 않지만 nonblocking 별도 thread이므로 영상에는 영향을 주지 않는다.
- HDMI 앱의 약 60 fps는 carrier다. 보안 영상 acceptance rate는 RX authenticated/display content 약 30 fps로 판정한다.
