# RSA 세션 키·BTN3 실기 검증 기록 (2026-08-05)

## 검증 대상

- 보드: Zybo Z7-20 TX/RX 각 1대
- 툴: Vivado/PetaLinux 2025.2
- 부팅: 최종 BIT와 최종 PetaLinux 이미지를 JTAG RAM 부팅
- 영상: Pcam → TX → 유선 Ethernet → RX → HDMI, 1280×720 YUYV 약 30fps
- 제어: TX/RX ipTIME N150UA, RSA-2048 OAEP-SHA256 세션 키 교환
- 스위치: TX/RX SW3 ON, TX SW2 세션 요청, TX BTN3 세션 종료/재시작

이 문서는 이 폴더의 최종 산출물을 대상으로 한 결과다. `1. 베이스_완성본`은 RSA가 없는 별도 기준본이며 이 검증 과정에서 수정하지 않았다.

## BTN3 반복 결과

TX BTN3 누름 유지 시 양쪽 키가 삭제되고 새 프레임이 시작되지 않아 RX HDMI가 마지막 정상 프레임을 유지했다. BTN3를 떼면 TX가 새 난수 AES-256 키와 새 session ID/counter/RSA capsule을 만들고, 양쪽 PL commit 완료 뒤 영상이 사용자 재부팅이나 수동 서비스 재시작 없이 복구됐다.

관찰된 세션 순서:

| RSA counter | session ID | 다음 동작 |
|---:|---|---|
| 1 | `EE8BCFD0` | BTN3 종료 |
| 2 | `EF8CE1A5` | BTN3 종료 |
| 3 | `9143579D` | 정상 commit |
| 4 | `B4B29A45` | BTN3 종료 |
| 5 | `00DEC9C0` | 정상 commit, 최종 활성 |

최종 상태:

- TX/RX active session: `00DEC9C0`
- TX/RX key valid/ready: `1/1`
- TX/RX key epoch: `5`
- TX request count: `5`
- TX termination count: `3`
- TX 세션 에이전트/영상 서비스: running
- RX 세션 에이전트/영상 서비스: running
- HDMI 영상: 약 29~30fps로 부드럽게 재개

RX의 당시 `auth_fail=75`, `lost total=163`은 BTN3 강제 종료, SW2/SW3 전환, 링크 복구 시험을 반복하며 누적된 값이다. 정상 안정 구간의 신규 오류율로 해석하면 안 된다. 이후 steady-state 시험은 시작 counter를 기록하고 일정 시간 뒤 증가량으로 판단한다.

## 현재 세션 수명

이 1차 변형은 시간 기반 자동 재키를 하지 않는다. 새 키는 TX SW2 OFF→ON, TX BTN3 해제, 새 부팅에서만 만들어진다.

- nonce: `session_id 32비트 + frame_id 32비트 + 0 16비트 + packet_index 16비트`
- 프레임당 packet: 1,280개
- 패킷당 payload CTR 블록: 90개 (`counter=2..91`)
- 동일 세션의 nonce 구조상 한계: `2^32` 프레임
- 30fps 환산: 약 1,657일, 4.54년

4.54년은 권장 운용 주기가 아니라 nonce가 다시 겹치기 전에 반드시 재키해야 하는 구조적 상한이다. 자동 1시간 재키 같은 정책은 다음 데모 파생본에서 별도 구현·검증한다.

## SD 부팅 검증 이력과 자동복구 수정

첫 TX/RX SD cold boot에서 Linux, 유선망, Wi-Fi와 RSA 세션 서비스는 정상 기동했지만 HDMI 영상이 자동 시작되지 않는 경쟁 조건을 발견했다. 당시 TX 영상 init은 세션 키를 최대 300초 기다린 뒤 준비 여부와 무관하게 송신기를 한 번 실행했고, 송신기는 `AES session registers are not ready`로 종료됐다. 이후 RSA 세션이 성공해도 one-shot init이 송신기를 다시 시작하지 않아 화면이 계속 멈췄다. TX에서 `/etc/init.d/pcam-gcm-tx restart`를 실행하자 즉시 DMA-BUF 경로가 시작됐고 RX에서 약 26~29fps, `lost total=0`, `auth_fail=0`, `status_fail=0`, `queue_overrun=0`으로 복구됐다.

최신본은 TX 영상 서비스를 백그라운드 supervisor로 바꿔 키·카메라·DMA가 늦게 준비돼도 계속 기다린 뒤 자동 시작하고, 프로세스가 종료되면 2초 뒤 다시 준비 상태부터 확인한다. RX init은 런타임 준비를 계속 기다린 뒤 한 번 시작하며, RX 본체의 UDP 피어 탐색은 기존처럼 무한 재시도한다.

실기에서 RX 프로세스 강제 재시작 감시도 시험했으나, 진행 중인 DMA를 끊으면 PL 스트림 엔진이 중간 프레임 상태에 남아 새 프로세스가 `DMAengine status=-110 MM2S=1 S2MM=0`을 반복했다. RX 보드 재부팅 후 약 27fps로 정상 복구됐다. 따라서 검증되지 않은 RX 무한 프로세스 재실행은 최종본에서 제거했고, fatal DMA timeout의 안전 복구는 RX 보드/PL 재부팅으로 명시했다. PetaLinux 2025.2 최종 재빌드 후 `rootfs.cpio.gz`에서 두 init 스크립트가 소스와 byte-for-byte 일치하는지 다시 확인한다.

## 최신 SD 실기 검증: 부팅 순서와 한쪽 재부팅

두 카드에는 각 역할의 `sd_card/`와 같은 8개 항목만 복사하고 `SHA256SUMS`를 보드에서 직접 검증했다. 카드의 ext4 파티션에는 TX counter와 RX의 인증된 RSA capsule/phase를 영속화하되 평문 AES 키는 기록하지 않는다.

검증 결과는 다음과 같다.

1. TX 단독 재부팅: RX를 켜 둔 상태에서 TX만 재부팅하자 counter가 3에서 4로 증가하고 새 세션 `7AB33870`이 자동 수립됐다. 수동 로그인이나 서비스 재시작은 필요하지 않았다.
2. RX 단독 재부팅: TX와 세션 4를 유지한 채 RX만 재부팅하자 저장된 ACTIVE capsule을 복호화해 같은 키를 PL에 재적용했다. 로그는 `RX restored active session 7ab33870 into PL after reset`과 `RX recovered session 7ab33870 counter 4 (active)`였다.
3. 최종 레지스터: TX/RX active session `0x7AB33870`, 양쪽 key valid/ready `1/1`, busy/error/pending `0`.
4. 서비스: TX/RX 세션 에이전트와 영상 서비스 모두 `running`, N150UA WPA 상태 `COMPLETED`.
5. 영상: RX 1280x720 YUYV UDP가 26.1~29.3fps로 자동 재개됐다. `auth_fail=0`, `status_fail=0`, `queue_overrun=0`, `stale=0`; 의도적인 RX 재부팅 구간의 누적 손실은 5프레임이었다.

이 결과로 최신 SD 본에서는 TX 먼저, RX 먼저, TX 단독 재부팅, RX 단독 재부팅 모두 사용자 스위치나 로그인 없이 자동 수렴하도록 확인했다. 로그인은 진단 명령을 실행하기 위해서만 사용했으며 서비스 시작 조건이 아니다.
